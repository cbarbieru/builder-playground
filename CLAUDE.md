## Additional context

> Note: Builder Playground is no longer actively maintained (stable, but no new features). The successor project is [decker](https://github.com/flashbots/decker).

### What this tool does

A CLI (`builder-playground`) that spins up self-contained Ethereum devnets (L1 and L2/OpStack) via Docker Compose, purpose-built for testing block-building/MEV pipelines (mev-boost, relays, builders) rather than general-purpose chain simulation.

### CLI surface (`main.go`)

Cobra commands, all defined in `main.go`: `start <recipe>`, `stop`, `clean`, `validate <recipe>`, `debug inspect`, `logs`, `dir`, `list`, `port`, `generate <recipe>`, `generate-docs`, `recipes`, `version`, `test`. `start`/`generate` accept either a base recipe name (`l1`, `opstack`) or a path to a custom recipe YAML file.

### Recipe interface (`playground/manifest.go`)

```go
type Recipe interface {
    Name() string
    Description() string
    Flags() *flag.FlagSet
    Artifacts() *ArtifactsBuilder
    Apply(ctx *ExContext) *Component
    Output(manifest *Manifest) map[string]interface{}
}
```
Base recipes are registered in `GetBaseRecipes()` (`playground/manifest.go`): `L1Recipe`, `OpRecipe`, `BuilderNetRecipe`. Components are registered separately in `playground/catalog.go`'s `init()`.

### Custom recipes (`docs/custom_recipes.md`, `playground/custom_recipes.go`)

A YAML file with `base: <recipe-name>` plus a `recipe:` map that overrides/adds/removes services on top of a base recipe (e.g. bump an image tag, swap a binary). Pre-built ones live under `custom-recipes/` (e.g. `custom-recipes/rbuilder`, `custom-recipes/buildernet`) and are embedded into the binary via `//go:embed custom-recipes/*` in `main.go`. Run with `builder-playground start <path-or-name>`; inspect one with `builder-playground generate <name>`.

### Supporting binaries/packages (separate Go modules-in-spirit, same repo)

- `mev-boost-relay/` — in-memory MEV-Boost relay (in-memory DB + embedded miniredis, mock block validation) used by the `l1`/`opstack` recipes instead of a production relay stack.
- `cl-proxy/` — Engine API multiplexer that lets a beacon node drive a primary EL plus a secondary EL/builder side-by-side (used for `--secondary-el`/dual-builder testing).
- `healthmon/` — health-monitoring/watchdog sidecar (backs the `--watchdog` flag).
- `utils/` — shared helpers: `paths.go`, `pet_name.go` (session name generation), `detached.go` (background/detached run support), `keys/` (key + BLS fixtures), `logging/`, `mainctx/`.
- These are wired into recipes as Docker services through `playground/components.go`, not imported as libraries by the CLI logic directly.

### Docs layout (`docs/`)

`docs/recipes/*` is auto-generated by `make generate-docs` (via `playground/docs.go`) from each recipe's `Flags()`/`Description()` — do not hand-edit generated recipe docs, change the source and regenerate. `docs/custom_recipes.md` and `docs/custom_recipes_guide.md` are hand-written. CI (`docs-check` job in `.github/workflows/checks.yaml`) fails if generated docs are stale, so run `make generate-docs` after touching recipe flags/descriptions and commit the result.

### Testing

- `make test` → `go test -v -count=1 ./...` (unit tests).
- `make e2e-test` → builds the binary then runs `E2E_TESTS=true go test -v -count=1 ./e2e/...`, which actually starts recipes via Docker Compose and asserts against live services (see `e2e/e2e_test.go`, `e2e/recipes_test.go`). Requires Docker/Docker Compose.
- CI also runs plain `go test -v ./playground/...` as a separate unit-test job.

### Linting

`make lint` runs `gofmt -d -s`, `gofumpt -d -extra`, `go vet`, and `staticcheck` (golangci-lint config exists in `.golangci.yaml` but is currently commented out of the `lint` target). `make fmt` applies `gofmt`, `gci`, `gofumpt`, and `go mod tidy`. CI's lint job additionally verifies `go mod tidy` produces no diff.
